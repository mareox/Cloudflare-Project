Deliverable 2a: Implementation Steps

Configured Cloudflare DNS

Created proxied DNS for tunnel.mareoxlan.com using a CNAME to the existing Cloudflare Tunnel target.

Deployed the origin server

Ran a Flask and gunicorn header echo service on a private homelab Docker host at http://<private-origin-ip>:18088. The origin exposes /healthz and returns request data as JSON.

Enabled Full Strict TLS

Set the zone SSL mode to Full Strict for origin certificate validation during the proxy phase.

Moved traffic behind Cloudflare Tunnel

Added a Tunnel public hostname mapping tunnel.mareoxlan.com to http://<private-origin-ip>:18088, removing the need for inbound public firewall exposure.

Protected /secure* with Access

Created a self-hosted Access app for tunnel.mareoxlan.com/secure* with Google IdP and allow policies for the owner plus Cloudflare reviewer addresses.

Deployed Worker and R2

Created private R2 bucket country-flags, uploaded us.svg, and deployed Worker cf-application-secure on /secure and /secure/*.

Deliverable 2b: Relevant Use Cases

Product Use case
Cloudflare DNS Routes the public hostname and keeps traffic proxied through Cloudflare.
Cloudflare Tunnel Publishes a private homelab service without exposing inbound ports.
Cloudflare Access Enforces identity-aware access before requests reach the application.
Workers Runs edge logic on protected routes and uses Access identity headers.
R2 Stores private static assets and serves them only through a Worker binding.

Deliverable 2c: Knowledge Gaps Filled

Access identity in Workers

I verified when the Access policy runs relative to the Worker. Because Access protects /secure*, the Worker receives requests only after policy success and can use Cf-Access-Authenticated-User-Email.

Private R2 access

I confirmed that a Worker binding is the authorization mechanism for private R2 reads. No public bucket domain or signed URL is required.

Route ownership

I validated that only /secure and /secure/* are Worker routes, while the root path continues to the origin through Tunnel.

Customer Experience

A target customer would find the result compelling because a private internal app becomes internet-accessible without opening inbound firewall paths. Access adds identity controls at the edge, Workers add custom behavior without changing the origin, and R2 keeps static assets private.

The main setup friction is product boundary alignment: DNS points to Tunnel, Tunnel points to the origin, Access owns the protected path, Worker route patterns must match that path, and R2 is available only through the binding. Once that request path is understood, the solution is clean and repeatable.
