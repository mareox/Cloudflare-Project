Deliverable 2a: Implementation Steps

Configured Cloudflare DNS

Created proxied DNS for tunnel.mareoxlan.com using a CNAME to the existing Cloudflare Tunnel target.

Deployed the origin server

Ran a Flask and gunicorn header echo service on a private homelab Docker host at http://<private-origin-ip>:18088. The origin exposes /healthz and returns request data as JSON.

Enabled Full Strict TLS

Set the zone SSL mode to Full Strict for origin certificate validation during the proxy phase.

Moved traffic behind Cloudflare Tunnel

Added a Tunnel public hostname mapping tunnel.mareoxlan.com to http://<private-origin-ip>:18088, removing the need for inbound public firewall exposure.

Protected /secure* with Access

Created a self-hosted Access app for tunnel.mareoxlan.com/secure* with Google IdP and allow policies for the owner plus Cloudflare reviewer addresses.

Deployed Worker and R2

Created private R2 bucket country-flags, uploaded us.svg, and deployed Worker cf-application-secure on /secure and /secure/*.

Deliverable 2c: Knowledge Gaps Filled

Access identity in Workers

I verified when the Access policy runs relative to the Worker. Because Access protects /secure*, the Worker receives requests only after policy success, then validates Cf-Access-Jwt-Assertion against Cloudflare Access certificates before displaying the authenticated identity.

Private R2 access

I confirmed that a Worker binding is the authorization mechanism for private R2 reads. No public bucket domain or signed URL is required.

Route ownership

I validated that only /secure and /secure/* are Worker routes, while the root path continues to the origin through Tunnel.

Customer Experience

A target customer would find the security outcome immediately compelling: a private internal app becomes internet-accessible without exposing the origin IP, without opening inbound firewall rules, and without a VPN. Access adds identity controls at the edge before the request reaches the Worker or origin. Workers add custom logic without changing the origin server. R2 stores assets privately and serves them only through the Worker binding.

The main setup friction is product-boundary alignment. DNS points to Tunnel, Tunnel points to the origin, Access owns the protected path, Worker route patterns must match that path, and R2 is available only through the binding. A misconfigured route pattern (e.g., /secure without the trailing /*) causes the Worker to miss sub-paths. These are one-time configuration steps with good error messages, and a clear onboarding sequence resolves them quickly.

The long-term value is high for internal tooling, partner portals, admin applications, and lightweight SaaS products. Adding a second protected application or a new Worker route is incrementally simpler after the first deployment — each new service reuses the existing Tunnel, IdP, and R2 bucket.

Best Practices Applied

Full Strict TLS

Cloudflare validates the origin certificate chain. Prevents MITM between Cloudflare and the origin even if the origin IP were somehow discovered.

No inbound firewall holes

The origin runs behind Cloudflare Tunnel. cloudflared makes outbound-only connections — no public IP, no open port on the host.

Default deny on Access

The Access app blocks by default. Only explicitly listed identities receive a JWT. No implicit permit for authenticated users.

Private R2 with Worker binding

The country-flags bucket has no public access. The Worker R2 binding is the only read path — no access keys or signed URLs in code.

Security response headers

All HTML responses carry X-Content-Type-Options, X-Frame-Options: DENY, Referrer-Policy, Permissions-Policy, and a strict Content-Security-Policy.

HTML output escaping

All user-controlled values (email, country, timestamp) are escaped through escapeHtml() before HTML insertion, preventing reflected XSS.
